# 微博舆情分析系统 — 项目全面评估与开发规划

> 评估日期：2026-07-30
> 评估范围：后端架构、前端 UI/UX、数据层、测试体系、部署运维、配置管理、文档、安全、技术债务
> 评估方法：4 个专项审计（后端架构 / 前端 / 文档与债务 / 测试与运维）+ 代码结构量化

---

## 一、评估概述

### 1.1 项目定位

微博舆情分析系统，覆盖"数据采集 → 存储 → NLP 分析 → 情感计算 → 预警 → 通知 → 可视化"全链路。技术栈：Python 3.11 / Flask / Celery / MySQL(FTS5 SQLite 辅助) / Redis / SnowNLP+BERT / Vue 3 + ECharts。

### 1.2 整体评级

| 维度 | 评级 | 一句话结论 |
|---|---|---|
| 后端架构 | 🟢 良好 | 分层清晰，新代码质量高，但存在死代码与上帝文件 |
| 功能完整性 | 🔴 严重不足 | 多平台采集、短信通知、预警持久化均为占位/缺失 |
| 数据层 | 🔴 严重风险 | ORM 与 DB schema 错位，Alembic 形同虚设 |
| 前端 UI/UX | 🟢 良好 | 技术栈现代，但多处用 mock/静态数据冒充真实 |
| 测试体系 | 🟡 中等 | 核心服务单测覆盖优秀，但套件 hang、门禁弱 |
| 部署运维 | 🔴 严重风险 | compose 缺主应用 Celery worker、镜像臃肿、密钥默认值不安全 |
| 配置管理 | 🟡 中等 | .env 完整但默认值与文档/代码多处不一致 |
| 文档 | 🔴 严重滞后 | 22 份文档 7 组重叠，多份与代码矛盾 |
| 安全 | 🟢 总体良好 / 🔴 局部 | 设施完备，但 `pickle.load` 与明文种子密码未治理 |

### 1.3 核心结论

项目**架构底子好、单测纪律好**，但**"看起来能用"与"真能上生产"之间存在系统性差距**：多个核心环节是占位实现（采集器返回假数据、短信永不送达、预警重启即丢），且前端用 mock 数据冒充真实图表，构成"虚假完成度"。生产化前需先堵住这些断裂点。

## 二、项目现状总览

### 2.1 规模

- **后端服务**：`src/services/` 下 30+ 服务文件/包；13 个 API 蓝图，68 个端点
- **前端**：`frontend/` Vue 3 SPA，18 个业务页 + 3 个错误页
- **微服务**：`spider_service/`（端口 8090）、`nlp_service/`（端口 8091）各带独立 Flask+Celery
- **测试**：68 个测试文件，约 1299 个用例
- **文档**：`docs/` 22 份 .md + 子目录
- **部署**：docker-compose 编排 8 个服务（mysql/redis/web/frontend/spider-api/spider-worker/nlp-api/nlp-worker）

### 2.2 架构拓扑

```
Vue3 SPA ──nginx──> 主服务(src/) ──HTTP──> spider_service/ (独立 Flask+Celery)
                                       ──HTTP──> nlp_service/   (独立 Flask+Celery)
                                       ──Celery──> src/tasks/    (本地 Celery)
```

- 三级任务状态回退链（spider remote → nlp remote → local Celery）实现严谨
- 3 个独立 Celery 实例（主 + spider + nlp），运维复杂度高
- 无服务发现、无熔断/限流，远程故障靠 try/except + 超时兜底

### 2.3 已完成的高质量工作（值得肯定）

- `sentiment_service/` 包：策略模式 + 自适应选择 + 多后端 + 缓存 + 监控，架构优秀
- `views/api/api.py` 从 1041 行上帝文件拆分为 `_shared.py` + 5 个 `*_routes.py`
- 核心服务单测覆盖：alert/notification/search/nlp_task/spider_task/sentiment 等多个达 100%
- CSRF 纵深防御（Origin/Referer + SameSite）、日志脱敏、加密/限流/输入校验工具齐备
- 前端 axios 拦截器、token 内存存储（不落 localStorage）、HttpOnly Cookie+Bearer 双轨认证
- PWA、暗黑模式、移动端响应式、拖拽自定义仪表盘、Keep-alive 多标签

## 五、性能瓶颈嫌疑点

1. **NLP 模型导入耗时 ~50s**：`from services.sentiment_service.models import SentimentResult` 触发模型加载，所有 sentiment 测试与启动都承担此成本。建议：模型懒加载（首次分析时再加载），或预热异步化。
2. **`database.py` 无 connect_timeout**：MySQL 故障时连接无限阻塞，拖垮应用启动与测试。
3. **3 个 Celery 实例无统一调度**：无 celery beat，定时任务（预警扫描、变点检测）无触发。
4. **SQLAlchemy engine 日志 INFO**：生产环境产出大量冗余 SQL 日志。
5. **Docker 镜像 2-4GB**：torch/transformers 全量装入，启动慢、拉取慢。
6. **前端 BigScreen 5s 轮询 3 个分散接口**：未用 `/api/bigscreen/all` 批量端点。
